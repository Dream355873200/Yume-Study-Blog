## 漫剧智能创作平台系统设计方案

### 一、 整体功能架构 (System Architecture)

该平台采用分层架构设计，确保从用户入口到核心 AI 创作引擎的流程顺畅。

1. **用户中心 (User Center)**
    
    - **登录注册：** 支持手机/邮箱登录。
        
    - **身份切换：** 登录后进入“控制面板”，选择 **个人工作台** 或 **团队工作台**。
        
2. **团队协作系统 (Collaboration)**
    
    - **社交系统：** 好友申请、群聊/私聊（项目同步）。
        
    - **权限管理：** * **Leader：** 拥有资产删除权、成员管理权。
        
        - **Member：** 拥有创作权、编辑权。
            
    - **资产分发：** 个人库资产可一键“推送到团队库”。
        
3. **核心创作引擎 (Creative Pipeline)**
    
    - **剧本分析：** 自然语言处理（NLP）拆解角色、场景、分镜。
        
    - **Agent 协作层：** 基于 CoT（思维链）的图像生成与重绘。
        
    - **后期合成：** Wasm FFmpeg 实时剪辑系统。

### 二、 逻辑流程设计

#### 1. 工作流概览

项目采用 **“分集开发”** 模式，每一集遵循以下线性流程，但允许在库之间自由跳转：

`剧本分析` -> `角色设计` -> `场景设计` -> `镜头生成` -> `视频剪辑`

#### 2. 详细功能模块说明

| **模块名称**          | **核心功能描述**               | **协作/Agent 逻辑**                                       |
| ----------------- | ------------------------ | ----------------------------------------------------- |
| **项目管理**          | 分个人项目/团队项目，按“集”管理。       | 只有 Leader 可执行 `Delete` 操作，防止误删。                       |
| **剧本分析**          | 结构化剧本，自动提取角色特征、环境描述。     | Agent 自动生成初步的 Prompt 库。                               |
| **角色/场景设计**       | <u>提供模板（分镜模板、参考图模板）。</u> | **对话式重绘：** Agent 携带卡片元数据（ID, Prompt, Context），支持增量修改。 |
| **资产库 (Library)** | 共享库：角色、模板、素材、剧本。         | 个人资产在审核/勾选后可并入团队共享库。                                  |
| **Wasm 剪辑器**      | 浏览器端基于 FFmpeg 的轨道剪辑。     | 支持拖拽生成的镜头，实时预览，无需上传后台。                                |

### 四、 Agent 交互逻辑 (Chain of Thought)
## 1. Agent 核心架构模式：PEER 循环

我们将 Agent 升级为一个**智能体编排系统**，遵循 **PEER (Plan - Execute - Evaluate - Refine)** 循环。

- **Planner (规划者):** 负责解构用户模糊需求，拆解为有序的子任务队列。
- **Executor (执行者):** 逐个领取子任务，调用具体工具（绘画、文案、检索）。
- **Observer (观察者):** 负责检索上下文（Context Retrieval）和审查结果（Criticism），确保生成内容符合“设定集”。

## 2. 增强型思维链协议 (Rich Tag Protocol)

为了支持规划和执行的解耦，以及前端的可视化展示，定义以下 XML 标签集：

| 标签 (Tag)         | 描述 (Description) | 用途                               |     |
| ---------------- | ---------------- | -------------------------------- | --- |
| `<intent>`       | **意图识别**         | 分析用户输入的真实目的（是修改、新建还是闲聊）。         |     |
| `<context>`      | **知识装载**         | 显示 Agent 读取了哪些设定（如：读取了“主角发型”设定）。 |     |
| `<plan>`         | **全局规划**         | 展示生成的 Task List（任务列表）。           |     |
| `<step id="x">`  | **子任务**          | 包裹当前的执行步骤。                       |     |
| `<reasoning>`    | **推理过程**         | 当前步骤的具体思考逻辑（CoT）。                |     |
| `<tool_call>`    | **工具调用**         | 发起 API 请求的参数。                    |     |
| `<observation>`  | **观察结果**         | 工具返回的数据摘要。                       |     |
| `<reflection>`   | **自我反思**         | 判断当前步骤是否成功，是否需要修正。               |     |
| `<final_answer>` | **最终交付**         | 产出的最终文本或图片 URL。                  |     |

## 3. 详细交互案例 (Run-Time Example)

**场景：** 用户在一个古风项目中，对着一张“剑客站在雨中”的卡片说：

> **用户指令：** “把雨天改成下雪，给他加一件红色的披风，要有一种悲伤的氛围。”

**后端 Agent 实时流式输出 (Stream Response)：**

## 4. 技术实现方案

### 4.1 后端实现 (Golang + Eino/LangChain)

为了实现上述的 Tag 流式输出和状态管理，后端需要维护一个 **Long-Running State Machine**。

**核心 Struct 定义：**

```go
<GO>

// internal/agent_engine/planner.go

type AgentTask struct {

    ID          string

    Description string

    Status      string // Pending, Running, Done, Failed

    ToolOutput  string

}

type AgentState struct {

    SessionID   string

    ContextData map[string]interface{} // 存储检索到的上下文

    Plan        []*AgentTask           // 任务队列

    History     []Message              // 对话历史

}

// 核心执行器 loop

func (e *Engine) RunLoop(ctx context.Context, input string) (chan StreamEvent, error) {

    stream := make(chan StreamEvent)

    go func() {

        defer close(stream)

        // 1. Perception & Intent

        stream <- EmitEvent("<intent>Analyzing user request...</intent>")

        intent := e.AnalyzeIntent(input)

        // 2. Planning (调用 LLM 生成 XML/JSON 格式的 Plan)

        stream <- EmitEvent("<context>Loading assets...</context>")

        contextData := e.RetrieveContext(intent.TargetAssetID)

        stream <- EmitEvent("<plan>Drafting execution plan...</plan>")

        plan := e.GeneratePlan(input, contextData)

        // 3. Execution Loop

        for i, task := range plan.Tasks {

            stream <- EmitEvent(fmt.Sprintf("<step id='%d'>Starting task: %s</step>", i, task.Name))

            // ReAct within the step

            stream <- EmitEvent(fmt.Sprintf("<reasoning>%s</reasoning>", task.Reasoning))

            result, err := e.ExecuteTool(task.ToolName, task.Params)

            if err != nil {

                // 错误处理与重试逻辑

                stream <- EmitEvent("<reflection>Tool failed, retrying...</reflection>")

                // ... retry logic

            }

            stream <- EmitEvent(fmt.Sprintf("<observation>%v</observation>", result))

            task.ToolOutput = result

        }

        // 4. Final

        stream <- EmitEvent("<final_answer>...</final_answer>")

    }()

    return stream, nil

}

```
### 4.2 数据库支持 (PostgreSQL + Vector)

为了支持“规划”和“记忆”，数据库需要新增以下字段：

- **`agent_sessions` 表：** 存储一次复杂生成的完整生命周期，用于 Debug 和回溯。
    - `session_id` (PK)
    - `plan_snapshot` (JSON) - 最初的计划是什么
    - `execution_log` (Text/XML) - 实际执行的完整 Log
- **`asset_knowledge` (向量表)：**
    - Agent 需要知道“李逍遥”长什么样，需要将角色的文本描述 embedding 后存入向量库，以便 `<context>` 阶段检索。

### 4.3 前端展示逻辑 (React)

前端不再只是显示一个 Loading 转圈，而是解析 XML 标签渲染一个 **"思考进度组件"**。

- **组件：** `AgentThoughtProcess`
- **解析逻辑：** 使用流式 XML 解析器（如 `html-react-parser` 的魔改版或正则表达式流式匹配）。
- **UI 表现：**
    - 收到 `<plan>`：渲染一个 Checkbox 列表，随着 `<step>` 的推进自动打钩。
    - 收到 `<tool_call>`：显示一个小图标（例如：正在绘画... 正在修图...）。
    - 收到 `<reflection>`：显示一个黄色的警告条（例如：AI 觉得哪里不对，正在重试）。

## 5. 总结

通过引入 **PEER 循环** 和 **Rich Tag 协议**，这套新设计解决了以下问题：

1. **可控性增强：** 用户可以看到 Agent 的计划（Plan），如果计划第一步就错了（例如理解错了角色），用户可以由前端实现“打断”功能。
2. **复杂任务能力：** 支持链式修改（先改形、再改色、最后修脸），这是单步 Prompt 无法做到的。
3. **用户体验：** 将黑盒变成了白盒，漫长的生成等待时间（可能 20-30秒）变得有内容可看，减少焦虑。

### 六、 核心交互逻辑：资产版本链

针对“AI 生成内容皆资产”的理念，所有角色、场景、镜头的卡片均不再是“覆盖式”更新，而是“追加式”增长。

- **左右滚动浏览：** 点击任意卡片，进入全屏/半屏对比模式。通过鼠标滚轮或左右箭头查看该节点下的所有生成记录。
    
- **版本元数据锁定：** 每一张历史图都记录了当时的 $Seed$、全量 $Prompt$、参考图 $ID$ 和 $Agent$ 思维链过程。
    
- **资产固化：** 只有被用户手动标记为“选用”的版本，才会进入下游的分镜或剪辑系统。

#### 激进优化派（本地缓存 + 验证机制 - 推荐方案 🔥）

这是现代 App（如 Twitter、Notion）和高性能 Web 应用的做法。

- **做法**：
    1. **登录成功时**：把 Token 和 UserInfo（非敏感信息，如昵称、头像URL）一起存入 localStorage。
    2. **刷新页面时**：
        - **第 0ms**：立刻从 localStorage 读取 UserInfo，**瞬间渲染**出界面（显示头像和名字）。用户感觉是“秒开”，没有任何等待。
        - **第 100ms（后台悄悄进行）**：浏览器在后台默默发一个请求（比如 `/api/user/me`）去验证 Token 是否过期，并获取最新的用户信息。
        - **结果处理**：
            - **情况 A（正常）**：数据没变，什么都不用做，用户无感知。
            - **情况 B（数据变了）**：服务器返回了新头像，你用 React 的 state 更新一下，界面上的头像自动跳变成新的。
            - **情况 C（Token失效）**：服务器返回 401，说明 Token 过期了。这时候你再清空本地存储，把用户踢回登录页。
