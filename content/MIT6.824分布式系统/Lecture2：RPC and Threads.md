## 1. 为什么在分布式系统中使用线程？

在分布式系统中，线程（Go 中的 Goroutines）是处理并发逻辑的核心工具。

- **并发性 (I/O Concurrency)：** 分布式系统涉及大量网络等待。使用线程允许一个线程在等待网络响应（RPC）时，另一个线程继续处理计算任务或处理其他请求。
- **多核并行 (Parallelism)：** 充分利用多核 CPU 的计算能力。
- **便利性 (Convenience)：** 允许我们为每个任务编写顺序执行的代码逻辑，而不是复杂的事件驱动异步回调。

### 线程带来的挑战

- **共享数据竞争 (Race Conditions)：** 多个线程同时访问同一变量（如：两个线程同时修改 Map 计数）。
    - _解决：_ 使用锁（Sync.Mutex）或通过 Channel 通信。
- **协调 (Coordination)：** 一个线程需要等待另一个线程的结果。
    - _解决：_ 使用 Channel、Condition Variables 或 WaitGroup。
- **死锁 (Deadlock)：** 线程 A 等待 B，B 等待 A。



老师介绍了一个爬虫程序来详细解释为什么需要多线程和锁

教授展示了三个版本的爬虫：

- **Serial (串行):** 太慢，一次只能爬一个网页。
- **Concurrent (并发):** 使用 `go func()`。虽然快，但引出了**竞态条件 (Race Condition)**。多个线程同时检查 `fetched` 这个 Map（判断网页是否爬过）并尝试写入。
- **解决：** 引入了 `sync.Mutex`。这直接引出了分布式系统中“共享状态必须受保护”的核心观点。

## 2.异步编程和多线程的区别

 1. **同步编写方法 (Synchronous / Multi-threaded)**

这是 Go 采用的模型，也是教授在爬虫例子中重点展示的方式。

- **编写方式：** 代码是**顺序逻辑**。你写下 `data := fetch(url)`，程序会停在这里等待返回。拿到数据后，下一行代码继续处理。
- **并发实现：** 每一个并发任务（比如爬取一个新 URL）都开启一个独立的 **Goroutine**。
- **状态保存：** 这种方式最强大的地方在于，**状态保存在局部变量里（栈上）**。当一个 Goroutine 阻塞时，它的局部变量、调用栈都会被保留，等唤醒后继续执行。这对人类的逻辑思考非常友好。

2. **事件驱动方法 (Event-driven / Asynchronous)**

### 事件驱动方法 (Event-driven / Asynchronous)

这是像早期 Nginx 或 Node.js 经常采用的模型。

-  **编写方式：** 代码是**非线性**的。你发起一个请求（比如爬取网页），但你不能等待。你必须提供一个"回调函数 (Callback)"，然后立即结束当前函数的执行，回到主循环。

- **并发实现：** 通常只有一个或极少数几个线程。它通过一个"主循环 (Event Loop)"不断轮询网络是否有数据返回，有了数据就去调用你之前注册的那个回调函数。

- **状态保存（最麻烦的点）：** 教授提到，异步编程会产生 **"State Shredding" (状态破碎)**。因为函数已经返回了，局部变量都消失了。如果你想在数据回来后知道"我刚才是在爬哪个 URL"，你必须手动把这些状态存到一个全局的数据结构或闭包里。

```javascript

// 异步风格：逻辑分散

function crawl(url) {

    fetch(url, function(data) {       // 注册回调，立即返回

        var links = parse(data);

        links.forEach(function(link) {

            crawl(link);              // 回调中再发起请求

        });

    });

}
```

### 为什么事件驱动看起来像并发？

```text
┌─────────────────────────────────────────────────────────────┐
│                      Event Loop 原理                         │
└─────────────────────────────────────────────────────────────┘

    应用程序                          操作系统内核
    ────────                          ──────────
        │                                  │
        │  1. 发起网络请求 A               │
        │  ──────────────────────────────→ │  (非阻塞，立即返回)
        │                                  │
        │  2. 发起网络请求 B               │
        │  ──────────────────────────────→ │  (非阻塞，立即返回)
        │                                  │
        │  3. 调用 epoll_wait()            │
        │  ──────────────────────────────→ │  ← 阻塞在这里等待
        │                                  │
        │         (内核处理网络...)         │
        │                                  │
        │  4. 返回："A 和 B 都好了"         │
        │  ←────────────────────────────── │
        │                                  │
        │  5. 执行回调 A                   │
        │  6. 执行回调 B                   │
        │                                  │
        │  7. 再次调用 epoll_wait()...     │
```
它是这样一个逻辑，大部分时间在**等待网络/磁盘**因为回调执行的很快所以才能看似是并发执行，假如是计算密集型程序，那就和同步没有区别了。

在 Lecture 2 关于 Threads 和 Go 的演示中，教授（Robert Morris）特别强调了在开发分布式系统时，必须养成使用这个工具的习惯。



### 1. 如何使用

你只需要在执行 Go 命令时加上 `-race` 参数即可：

- **运行测试时（最常用）：**
    
```bash
    go test -race
```
    
- **运行程序时：**
    
```bash    
    go run -race main.go
```
    
- **编译程序时：**
```bash
    
    go build -race
```
    

### 2. 它能做什么？

当你在代码中开启了 `-race` 后，Go 编译器会在生成的可执行文件中插入一些**监测代码**。

- **实时监控：** 它会在程序运行时监控所有线程（Goroutines）对内存地址的访问。
- **检测冲突：** 如果它发现有两个 Goroutines 同时访问同一个变量，且**至少有一个是写入操作**，并且它们之间**没有适当的同步机制**（如锁 `Mutex` 或 `Channel`），它就会立即向终端打印一条详细的错误报告。
- **报告内容：** 报告会清晰地指出是哪两行代码产生了冲突，以及相关的 Goroutine 是在哪里创建的。

### 3. 课上提到的关键点（注意事项）

虽然这个工具非常强大，但也有它的局限性和代价：

1. **动态检测：** 它只能检测到**正在运行**的代码路径中的竞争。如果你的某段有 Bug 的逻辑在本次测试中没有被执行到，它就检测不出来。因此，配合高覆盖率的测试用例（Test Suite）使用效果最好。
2. **性能开销：** 开启 `-race` 会使程序运行变慢（通常是 2x 到 20x），并增加内存消耗（5x 到 10x）。所以，它**只应该在开发和测试阶段使用**，不要带到生产环境（Production）。
3. **ThreadSanitizer：** Go 的这个工具底层其实是基于 Google 的 `ThreadSanitizer`（C++ 也在用这个库）。
