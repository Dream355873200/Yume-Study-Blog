## 课程背景

第三课讲的是**大规模分布式存储**，教授讲述核心依然是分布式系统的四大主题：

- **Performance（性能）**
- **Fault Tolerance（容错）**
- **Replication（复制）**
- **Consistency（一致性）**

教授提到，Google GFS 是在**真实生产环境**运行的大型分布式存储系统，涉及**数十万台机器**，规模远超任何学术界的实践，因此比以往学术论文更具参考价值。

> **论文信息**：_The Google File System_, Sanjay Ghemawat, Howard Gobioff, Shun-Tak Leung, SOSP 2003

GFS 论文发布于 2003 年，正是互联网高速发展的时期（也是互联网泡沫破裂后的重建期），各大公司开始真正构建大型分布式系统。

## 从一个"最差设计"说起

教授用一个**最简单但最差的系统设计**引出了分布式存储的核心问题：

```text

┌──────────┐      ┌──────────┐

│ Client A │      │ Client B │

└────┬─────┘      └────┬─────┘

     │                 │

     ▼                 ▼

┌─────────────────────────┐

│      Single Server      │

│   (存储所有数据)          │

└─────────────────────────┘

```
**问题**：

- 单点故障（Single Point of Failure）
- 性能瓶颈（所有请求都打到一台机器）
- 数据竞争（多客户端并发读写）

## GFS 的设计特性

| 特性                        | 说明                |     |
| ------------------------- | ----------------- | --- |
| **Big**                   | 支持 PB 级数据存储       |     |
| **Fast**                  | 高聚合吞吐量            |     |
| **Global**                | 全局统一命名空间，任何人都能访问  |     |
| **Sharding**              | 大文件自动分片存储         |     |
| **Automatic Recovery**    | 自动故障恢复            |     |
| **Single Data Center**    | 仅部署在单一数据中心        |     |
| **Internal Use**          | 专为 Google 内部工程师设计 |     |
| **Big Sequential Access** | 针对大文件顺序读写优化       |     |

### GFS 的设计目标

> 构建一个**通用的大型存储系统**，让任何工程师都能共用同一个存储系统来访问和管理文件。GFS 会把大型文件**自动分片**并存入大量硬盘，以获得**高聚合吞吐量**。

### 关键设计假设（来自论文）

GFS 的设计基于 Google 对自身工作负载的观察：

1. **组件故障是常态**：成百上千台廉价机器，故障随时发生
2. **文件巨大**：通常是 100MB ~ 数 GB，甚至更大
3. **追加写为主**：几乎没有随机写，大多是 append
4. **顺序读为主**：大多数读取是顺序扫描大文件
5. **高吞吐优先于低延迟**：批处理场景居多

## GFS 架构

```text

                        ┌─────────────────┐

                        │     Master      │

                        │  (单一主节点)    │

                        └────────┬────────┘

                                 │ 元数据操作

            ┌────────────────────┼────────────────────┐

            │                    │                    │

            ▼                    ▼                    ▼

    ┌──────────────┐    ┌──────────────┐    ┌──────────────┐

    │ ChunkServer  │    │ ChunkServer  │    │ ChunkServer  │

    │   (64MB块)   │    │   (64MB块)   │    │   (64MB块)   │

    └──────────────┘    └──────────────┘    └──────────────┘

            ▲                    ▲                    ▲

            │                    │                    │

            └────────────────────┴────────────────────┘

                           数据流（直接传输）

                                 ▲

                                 │

                           ┌─────┴─────┐

                           │  Client   │

                           └───────────┘

```
### 核心组件

|组件|职责|
|---|---|
|**Master**|维护所有元数据，协调系统活动|
|**ChunkServer**|存储实际数据块（64MB/块）|
|**Client**|与 Master 交互获取元数据，直接与 ChunkServer 交换数据|

### 为什么选择 64MB 的 Chunk 大小？

**优点**：

- 减少 Client 与 Master 的交互次数
- 减少 Master 需要存储的元数据量
- Client 可以对一个大 Chunk 进行多次操作，复用 TCP 连接

**缺点**：

- 小文件可能只占一个 Chunk，导致热点问题
- （论文中提到，他们通过提高小文件的副本数来缓解）

## Master 节点的数据结构

Master 维护两张核心映射表：

```text

┌─────────────────────────────────────────────────────────────┐

│                    Master 内存数据结构                        │

├─────────────────────────────────────────────────────────────┤

│                                                             │

│  表1: filename → [chunk handle 数组]              (nv)      │

│       例: "/data/log.txt" → [h1, h2, h3, h4]               │

│                                                             │

├─────────────────────────────────────────────────────────────┤

│                                                             │

│  表2: chunk handle → chunk 元信息                           │

│       │                                                     │

│       ├── chunk servers 列表    (v)  [哪些服务器存了这块]    │

│       ├── version 版本号        (nv) [检测过期副本]          │

│       ├── primary 主副本        (v)  [谁是主]               │

│       └── lease expiration     (v)  [租约过期时间]          │

│                                                             │

└─────────────────────────────────────────────────────────────┘
```

(nv) = Non-Volatile，需要持久化到磁盘

(v)  = Volatile，可以从 ChunkServer 重建

### 持久化策略

```text

┌──────────────────┐

│   Operation Log  │ ──────→ 磁盘（本地 + 远程副本）

├──────────────────┤

│   Checkpoint     │ ──────→ 磁盘（B-tree 格式，可直接映射到内存）

└──────────────────┘
```

- **Operation Log**：记录所有元数据变更，是系统恢复的关键
- **Checkpoint**：定期快照，加速恢复过程
- **Chunk 位置信息不持久化**：启动时从各 ChunkServer 收集（因为 ChunkServer 才是"真相之源"）

### 为什么 Chunk 位置不持久化？

> _"A chunkserver has the final word over what chunks it does or does not have on its own disks."_

ChunkServer 自己最清楚自己有什么数据。与其让 Master 费力保持同步，不如每次启动时直接问。这样设计更简单、更可靠。

## 读操作流程

```text

Client                    Master                  ChunkServer

   │                         │                         │

   │ 1. 请求(filename,       │                         │

   │    chunk index)         │                         │

   │ ──────────────────────► │                         │

   │                         │                         │

   │ 2. 返回(chunk handle,   │                         │

   │    chunk locations)     │                         │

   │ ◄────────────────────── │                         │

   │                         │                         │

   │ 3. 请求数据(handle, byte range)                   │

   │ ─────────────────────────────────────────────────►│

   │                         │                         │

   │ 4. 返回数据                                        │

   │ ◄─────────────────────────────────────────────────│
```

**要点**：

- Client 缓存 chunk 位置信息，减少与 Master 的交互
- 数据直接从 ChunkServer 读取，不经过 Master
- Client 通常选择**最近的** ChunkServer 读取

## 写操作流程（重点！）

这是 GFS 最复杂也最精妙的部分：

```text

                          ┌─────────┐

                          │ Master  │

                          └────┬────┘

                               │ 2. 返回 primary 和

                               │    secondary 位置

          1. 请求 lease holder │

                ┌──────────────┴──────────────┐

                │                             │

                ▼                             │

          ┌──────────┐                        │

          │  Client  │                        │

          └────┬─────┘                        │

               │                              │

               │ 3. 推送数据到所有副本          │

               │    (任意顺序，链式传输)        │

               ▼                              │

    ┌──────────────────────────────────────────────┐

    │                                              │

    │   ┌─────────┐  ┌─────────┐  ┌─────────┐     │

    │   │Secondary│◄─│Secondary│◄─│ Primary │     │

    │   │ Replica │  │ Replica │  │ Replica │     │

    │   └─────────┘  └─────────┘  └────┬────┘     │

    │                                  │          │

    │         数据先缓存在 LRU buffer    │          │

    └──────────────────────────────────────────────┘

               │

               │ 4. 发送写请求到 Primary

               ▼

          ┌─────────┐

          │ Primary │ ── 5. 分配序列号，转发给 Secondary

          └────┬────┘

               │

               │ 6. Secondary 完成后回复 Primary

               │ 7. Primary 回复 Client

               ▼

          ┌──────────┐

          │  Client  │ ◄── 成功 or 失败（需重试）

          └──────────┘

```
### 写操作的七个步骤

|步骤|描述|
|---|---|
|**1**|Client 询问 Master：谁持有这个 chunk 的 lease？|
|**2**|Master 返回 Primary 和所有 Secondary 的位置|
|**3**|Client 将数据推送给**所有副本**（链式传输，利用网络拓扑优化）|
|**4**|所有副本确认收到数据后，Client 向 Primary 发送写请求|
|**5**|Primary 分配序列号，按序执行写操作，然后转发给所有 Secondary|
|**6**|Secondary 按相同序列号执行写操作，完成后回复 Primary|
|**7**|Primary 回复 Client（任一副本失败则报错，Client 重试）|

### 数据流与控制流分离

这是 GFS 的一个关键设计：

```text
控制流：Client → Primary → Secondary（确定写入顺序）

数据流：Client → 最近节点 → 次近节点 → ...（链式传输，优化带宽）
```

**好处**：

- 充分利用每台机器的出口带宽
- 利用网络拓扑，数据传给"最近"的下一跳
- 流水线传输，降低延迟

## Lease（租约）机制

```text

┌─────────────────────────────────────────────────────────┐

│                    Lease 机制                            │

├─────────────────────────────────────────────────────────┤

│                                                         │

│  • Master 授予某个副本 Primary 身份（60秒租约）            │

│  • Primary 负责确定所有写操作的顺序                       │

│  • 租约可续期（通过 HeartBeat 消息）                      │

│  • Master 可以在租约过期前撤销（如 rename 操作时）         │

│  • 如果 Master 与 Primary 失联，等租约过期后重新授权       │

│                                                         │

└─────────────────────────────────────────────────────────┘

```
**为什么需要 Lease？**

- 避免 Master 成为每次写操作的瓶颈
- 即使 Master 暂时不可达，Primary 仍可继续处理写请求
- 租约过期机制保证不会出现"双主"（Split Brain）

## Record Append（原子追加）

GFS 提供了一个特殊操作：**Record Append**

```text
普通 Write：Client 指定 offset

Record Append：GFS 选择 offset，保证原子性
```

### 使用场景

- 多生产者队列（多个 Client 并发追加到同一文件）
- 合并结果（多个 MapReduce Worker 写同一输出文件）

### 语义：At-Least-Once

```text
┌───────────────────────────────────────────────────────────┐

│  Record Append 可能导致：                                  │

│                                                           │

│  文件内容: [Record1][Record2][Record2][Padding][Record3]   │

│                      ↑                 ↑                  │

│                    重复              填充                   │

│                                                           │

│  • 保证每条记录至少写入一次                                 │

│  • 可能有重复、可能有填充                                   │

│  • 应用层负责去重（通过 checksum + unique ID）              │

└───────────────────────────────────────────────────────────┘

```

## 一致性模型

GFS 采用**宽松的一致性模型（Relaxed Consistency）**：

|操作类型|串行成功|并发成功|失败|
|---|---|---|---|
|**Write**|Defined（确定）|Consistent but Undefined（一致但未定义）|Inconsistent（不一致）|
|**Record Append**|Defined（确定）|Defined interspersed with inconsistent（确定区域夹杂不一致）|Inconsistent（不一致）|

### 术语解释

- **Consistent（一致）**：所有客户端看到相同的数据
- **Defined（确定）**：一致，且能看到完整的写入内容
- **Undefined（未定义）**：一致，但内容可能是多个写入的混合

### 为什么接受弱一致性？

> 为了性能，适当降低一致性是可以容忍的。

GFS 的目标应用（如 MapReduce）本身就是：

- 追加写为主
- 应用层可以处理重复和不一致（checksum、unique ID）
- 高吞吐比强一致性更重要

## 容错机制

### 1. Chunk 复制

```text
默认 3 副本，分布在不同机架

       │

       ├── 防止单机故障

       ├── 防止单机架故障（网络/电源）

       └── 读取时可以利用多机架带宽
```

### 2. Master 容错

```text
┌─────────────────────────────────────────┐

│            Master 容错策略               │

├─────────────────────────────────────────┤

│ • Operation Log 复制到多台机器           │

│ • 定期 Checkpoint                        │

│ • Shadow Master 提供只读服务             │

│ • 外部监控系统负责故障切换               │

└─────────────────────────────────────────┘
```

**注意**：GFS 的 Master 是**单点**，但不是单点故障——通过日志复制和快速恢复来保证可用性。

### 3. 版本号检测过期副本

```text
场景：ChunkServer C 宕机期间，chunk X 被修改

1. Master 授予新 lease 时，版本号 +1

2. 在线的副本更新版本号

3. C 恢复后上报旧版本号

4. Master 发现版本落后，标记为 stale（过期）

5. 过期副本不参与读写，等待垃圾回收
```

### 4. Checksum 检测数据损坏

```text
每个 64KB 块有一个 32-bit checksum

       │

       ├── 读取时校验

       ├── 空闲时扫描校验

       └── 发现损坏 → 从其他副本恢复

```

## GFS 的局限性

尽管 GFS 非常成功，但也有一些局限：

|局限|说明|
|---|---|
|**单 Master**|元数据量受限于单机内存，Master 可能成为瓶颈|
|**弱一致性**|应用需要自己处理重复和不一致|
|**单数据中心**|不支持跨地域部署|
|**大文件优化**|小文件性能不佳，可能产生热点|
|**追加优化**|随机写性能差|

> 后来 Google 开发了 **Colossus**（GFS2）来解决这些问题，但未公开发表论文。

## 总结

### GFS 的核心设计思想

1. **故障是常态**：设计系统时假设组件会频繁故障
2. **简单的中心化设计**：单 Master 简化了一致性和协调
3. **数据流与控制流分离**：优化网络利用率
4. **宽松一致性换性能**：应用层可以容忍
5. **针对工作负载优化**：大文件、顺序访问、追加写

### 课程核心问题

> 对于每一种想到的故障，系统为什么依然能够正确运行，或者为什么发生错误？

我认为这是研究任何系统的核心方法论——**Fault Reasoning（故障推演）**。
